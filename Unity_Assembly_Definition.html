01

한눈에 이해하기

왜 asmdef를 사용하는지부터 감을 잡아봅니다.

Assembly Definition File이란?

어떤 C# 스크립트들을 하나의 어셈블리(DLL)로 묶어 컴파일할지 정의하는 Unity 설정 에셋입니다. 확장자는 .asmdef입니다.

여러 장난감이 한 상자에 들어 있으면 정리가 어렵듯, 기능별로 스크립트를 나누면 컴파일 경계와 코드 간 의존성을 관리하기 쉬워집니다.

핵심 암기 폴더 구조 + asmdef + 참조 관계 = Unity 코드 모듈 구조
그림 1. 기본 어셈블리와 기능별 어셈블리의 차이
① 분리Core / UI / Gameplay
② 연결필요한 어셈블리만 참조
③ 재컴파일 관리영향 범위를 제한
④ 재사용테스트·패키지에 활용
중요한 오해 방지 asmdef를 생성한다고 게임의 실행 속도가 자동으로 빨라지는 것은 아닙니다. 주된 이점은 스크립트 컴파일·프로젝트 구조·의존성 관리입니다. 실제 컴파일 시간 개선 폭은 프로젝트 구조와 변경된 코드에 따라 달라집니다.
02

기본 개념 4가지

어셈블리 / 네임스페이스 / 참조 / 스크립트 폴더는 서로 다른 개념입니다.

🧩

어셈블리(Assembly)

C# 코드가 컴파일된 단위입니다. Demo.Core.dll 같은 DLL이라고 생각하세요.

📂

폴더

소스 파일의 물리적 위치입니다. asmdef는 폴더 아래의 스크립트 소속을 정합니다.

🏷️

네임스페이스

namespace AsmdefLab.Core처럼 C# 타입 이름을 구분하는 체계입니다. 어셈블리와 별개입니다.

🔗

참조(Reference)

A 코드가 B 어셈블리에 정의된 타입을 사용한다면 A가 B를 참조해야 합니다.

❌ 틀리기 쉬운 생각

“using AsmdefLab.Core;만 추가하면 다른 asmdef의 클래스를 쓸 수 있다.”

→ using은 이름을 찾기 쉽게 해 줄 뿐, 어셈블리 참조를 연결하지 않습니다.

✅ 정확한 이해

① 참조 설정으로 컴파일러가 해당 DLL을 알게 하고, ② public 접근성과 ③ namespace / using이 맞아야 타입을 사용할 수 있습니다.

03

asmdef의 적용 범위

하위 폴더를 포함하지만 다른 asmdef / asmref가 경계를 다시 정합니다.

그림 2. 어셈블리 정의의 폴더 소속 범위
기억하세요 동일한 폴더와 하위 폴더의 C# 파일이 속하지만, 하위 폴더에 또 다른 .asmdef나 .asmref가 있으면 해당 폴더부터 소속이 달라질 수 있습니다. 파일 위치만 옮겨도 어셈블리 경계가 바뀔 수 있습니다.

기존 프로젝트에 넣을 때 주의

기존 스크립트가 Assembly-CSharp에 있었다면 asmdef를 추가하는 순간 그 폴더의 스크립트가 새로운 어셈블리로 이동합니다. 다른 스크립트가 Assembly-CSharp의 타입을 사용하던 경우, 참조 방향 제한 때문에 구조 변경이 필요할 수 있습니다. 처음에는 별도 실습 폴더에서 시작하는 것이 안전합니다.

C# 스크립트 3개 작성

아래 코드를 각 폴더에 그대로 만들어 붙여 넣으세요. 코드 복사 버튼이 있습니다.

A

Core : Health.cs

Assets/AsmdefLab/Runtime/Core/Health.cs 생성. System.Math를 이용하는 순수 C# 체력 클래스입니다. MonoBehaviour가 아니므로 GameObject에 붙이지 않습니다.

Runtime/Core/Health.csC#
using System;

namespace AsmdefLab.Core
{
    // UnityEngine 없이 동작하는 순수 C# 체력 모델입니다.
    public sealed class Health
    {
        public int Maximum { get; }
        public int Current { get; private set; }

        public Health(int maximum)
        {
            if (maximum <= 0)
                throw new ArgumentOutOfRangeException(nameof(maximum));

            Maximum = maximum;
            Current = maximum;
        }

        public void Damage(int amount)
        {
            if (amount < 0)
                throw new ArgumentOutOfRangeException(nameof(amount));

            Current = Math.Max(0, Current - amount);
        }
    }
}

핵심: 체력 계산만 담당합니다. public으로 공개되어 다른 어셈블리에서 사용할 수 있습니다.

B

UI : HealthFormatter.cs

Assets/AsmdefLab/Runtime/UI/HealthFormatter.cs 생성. Health 클래스를 사용하므로 Demo.UI → Demo.Core 참조가 꼭 필요합니다.

Runtime/UI/HealthFormatter.csC#
using AsmdefLab.Core;

namespace AsmdefLab.UI
{
    // Health 타입을 사용하므로 Demo.Core 참조가 필요합니다.
    public static class HealthFormatter
    {
        public static string Format(Health health)
        {
            if (health == null)
                return "HP: -";

            return $"HP: {health.Current} / {health.Maximum}";
        }
    }
}

핵심: using AsmdefLab.Core;뿐 아니라 Demo.Core에 대한 Assembly Definition Reference 설정이 있어야 합니다.

C

Gameplay : HealthDemo.cs

Assets/AsmdefLab/Runtime/Gameplay/HealthDemo.cs 생성. 이 스크립트만 MonoBehaviour입니다.

Runtime/Gameplay/HealthDemo.csC#
using AsmdefLab.Core;
using AsmdefLab.UI;
using UnityEngine;

namespace AsmdefLab.Gameplay
{
    // GameObject에 붙여 실행할 MonoBehaviour 컴포넌트입니다.
    public sealed class HealthDemo : MonoBehaviour
    {
        [SerializeField] private int maximumHealth = 100;
        [SerializeField] private int damage = 25;

        private void Start()
        {
            // 서로 다른 두 어셈블리의 코드를 사용합니다.
            var health = new Health(maximumHealth);
            health.Damage(damage);

            Debug.Log(HealthFormatter.Format(health));
        }
    }
}

핵심: Health 타입과 HealthFormatter 타입을 사용하므로 Demo.Core와 Demo.UI 모두 참조합니다.

참고: asmdef는 내부적으로 어떤 JSON으로 저장될까요?

먼저 Unity Inspector로 만드는 방법을 권장합니다. 아래는 이해를 돕기 위한 최소 형식의 예시이며, 프로젝트에서는 Unity가 만든 파일에 옵션이 더 들어갈 수 있습니다.

Demo.Core.asmdefJSON
{
  "name": "Demo.Core",
  "rootNamespace": "AsmdefLab.Core",
  "references": [],
  "autoReferenced": true,
  "noEngineReferences": true
}
Demo.UI.asmdefJSON
{
  "name": "Demo.UI",
  "rootNamespace": "AsmdefLab.UI",
  "references": ["Demo.Core"],
  "autoReferenced": true

Inspector 주요 항목 이해

처음에는 Name, Assembly Definition References, Auto Referenced만 알아도 시작할 수 있습니다.

항목의미실전 사용 예시
Name컴파일된 어셈블리 이름. 프로젝트 내 중복 불가Demo.Core
Root NamespaceVisual Studio / Rider 등의 새 스크립트 생성 기본 네임스페이스에 영향AsmdefLab.Core; 기존 소스 namespace를 자동 변경하지는 않음
Assembly Definition References다른 asmdef가 정의한 어셈블리를 참조Demo.UI에서 Demo.Core 추가
Use GUIDs다른 asmdef 참조를 이름 대신 에셋 GUID로 기록어셈블리 이름 변경 시 참조 안정성 개선
Auto Referenced기본 어셈블리(예: Assembly-CSharp)에서 이 어셈블리를 자동 참조할지기본 true, 꺼도 빌드 제외 옵션은 아님
Override References사전 컴파일된 DLL에 대한 참조를 직접 제어특정 DLL만 사용하고 싶을 때
Assembly References사전 컴파일 DLL(Plugin) 참조 목록Override References 활성화 시 설정
No Engine ReferencesUnityEngine / UnityEditor 자동 참조 제거순수 C# 로직을 별도 어셈블리로 관리
Platforms에디터·플랫폼별 어셈블리 포함/제외Editor 전용 도구 어셈블리
Define Constraints스크립팅 심볼에 따른 조건부 컴파일필요한 define이 있을 때만 어셈블리 사용
Version Defines패키지나 모듈의 버전에 따라 심볼 정의특정 패키지 버전에 대한 조건 분기
Allow 'unsafe' CodeC# unsafe 사용 허용보통 초급 실습에서는 필요 없음

Editor 전용 asmdef

UnityEditor API를 사용하는 코드는 별도 Demo.Editor.asmdef로 만들고 Platforms를 Editor만 포함하도록 설정합니다. Editor 코드가 런타임 코드에 의존하면 Editor → Runtime 참조는 가능합니다. 반대 방향은 불가능합니다.

패키지 코드와 연결

UPM 패키지 내부의 코드에는 보통 asmdef가 필요합니다. Unity UI Toolkit / Input System 등 다른 패키지가 제공하는 어셈블리 타입을 사용한다면 해당 패키지의 asmdef 참조가 필요한지 확인하세요. using만 추가해선 해결되지 않을 수 있습니다.

.asmref

① Assets/AsmdefLab/Runtime/ExtraCore 폴더 생성 → ② Assets > Create > Scripting > Assembly Definition Reference 생성 → ③ Inspector의 Assembly Definition에 Demo.Core 지정 → ④ Apply → ⑤ DamageMath.cs를 ExtraCore에 배치합니다.

ExtraCore/DamageMath.csC#
namespace AsmdefLab.Core
{
    // 별도 폴더에 있지만 .asmref 덕분에 Demo.Core로 컴파일됩니다.
    public static class DamageMath
    {
        public static int NonNegative(int value) => value < 0 ? 0 : value;
    }
}

실제 EditMode 테스트 어셈블리를 만들어 참조와 테스트 분리를 경험합니다.

1

Test Framework 설치 여부 확인

Window → Package Manager에서 Test Framework가 설치되어 있는지 확인합니다. Unity 6.3 기준 패키지 구성에 따라 표시 방식이 달라질 수 있습니다.

2

Test Runner에서 Test Assembly Folder 생성

Window → General → Test Runner를 열고 원하는 위치를 선택한 뒤 Create a new Test Assembly Folder를 실행합니다. 또는 Assets > Create > Testing > Test Assembly Folder를 사용할 수 있습니다.

3

테스트 어셈블리에 Demo.Core 참조 추가

Unity가 만든 Tests.asmdef를 선택하여 Assembly Definition References에 Demo.Core를 추가합니다. Test Runner가 자동 생성한 nunit.framework.dll, UnityEngine.TestRunner, UnityEditor.TestRunner 같은 필수 참조는 지우지 마세요.

4

HealthTests.cs 생성 후 EditMode 테스트 실행

테스트 어셈블리가 속한 폴더에 아래 코드를 만들고 Test Runner의 EditMode 목록에서 Run All을 누릅니다. 2개 테스트가 통과하면 성공입니다.

Tests/HealthTests.csC#
using AsmdefLab.Core;
using NUnit.Framework;

public class HealthTests
{
    [Test]
    public void Damage_25_From_100_Leaves_75()
    {
        var health = new Health(100);
        health.Damage(25);
        Assert.That(health.Current, Is.EqualTo(75));
    }

    [Test]
    public void Damage_Cannot_Go_Below_Zero()
    {
        var health = new Health(100);
        health.Damage(999);
        Assert.That(health.Current, Is.EqualTo(0));
    }
}

주의: 테스트 소스는 일반 Runtime 폴더에 두지 말고 Test Runner로 생성한 테스트 어셈블리에 넣으세요.

빌드 주의 Test Framework의 EditMode 테스트 어셈블리는 일반 플레이어 빌드에 포함되는 런타임 코드와 분리됩니다. UnityEditor.TestRunner는 EditMode 테스트에서 사용되며, PlayMode 플레이어 테스트의 참조 설정은 다릅니다.

자주 생기는 오류 해결

Console에서 처음 발생한 에러부터 확인하고 참조 관계를 살펴보세요.

가장 중요한 규칙 Assembly-CSharp가 사용자 asmdef를 자동 참조할 수는 있지만(기본 설정), 사용자 asmdef → Assembly-CSharp 방향의 참조는 Unity가 허용하지 않습니다. 순환 참조도 허용하지 않습니다.
?CS0246 / 타입을 찾을 수 없음

가능한 원인 사용 중인 asmdef에서 상대 asmdef를 참조하지 않음 / using 누락 / public 아님

해결 순서 ① 타입이 있는 어셈블리 확인 → ② Assembly Definition References 추가 → ③ public, namespace, using 확인

?Assembly-CSharp의 클래스를 asmdef에서 사용 불가

가능한 원인 사용자 정의 asmdef는 기본 Assembly-CSharp 어셈블리를 참조할 수 없음

해결 순서 공통 타입을 별도 Core asmdef로 옮기고 의존하는 쪽에서 Core 참조

?Cyclic reference / 순환 참조

가능한 원인 A → B와 B → A가 동시에 존재

해결 순서 공통 타입을 세 번째 Core 어셈블리로 분리하거나 서로 의존하는 타입을 같은 어셈블리로 구성

?MonoBehaviour를 컴포넌트로 추가할 수 없음

가능한 원인 컴파일 오류, 클래스 이름 불일치, Editor 전용/플랫폼 제외, 타입 접근성 등

해결 순서 Console 첫 번째 오류부터 해결하고 class/file 이름 및 asmdef Platforms 확인

?UnityEditor를 찾지 못함 / 빌드 실패

가능한 원인 Editor 전용 API가 Runtime asmdef에 포함되거나 플랫폼이 잘못 설정됨

해결 순서 Editor 전용 asmdef + Platforms: Editor만 선택; Runtime에서 Editor 참조 금지

?패키지 타입이 안 보임

가능한 원인 필요한 패키지 어셈블리 참조나 설치가 빠짐

해결 순서 Package Manager 설치 확인 → 패키지에서 제공하는 asmdef 참조 추가

?asmdef 이름 변경 이후 참조 오류

가능한 원인 이름 기반 참조를 사용하거나 Name 필드가 남아 있음

해결 순서 Name과 파일명 차이 확인; 가능하면 Use GUIDs 및 참조 상태 재검증

?한 파일만 수정했는데 재컴파일이 많음

가능한 원인 하위/상위 의존 관계, 자동 참조, 코드 생성기·에디터 리로드 등 영향

해결 순서 참조 방향과 Auto Referenced 여부 점검; 실제 컴파일/리로드 시간을 측정

실무 설계 패턴

프로젝트가 커지면 Game.Core, Game.Gameplay, Game.UI, Game.Data, Game.Editor, Game.Tests 등으로 역할별 분리할 수 있습니다. 단, 무조건 많이 쪼개는 것보다 실제 독립적으로 관리할 이유가 있는 경계를 먼저 찾으세요.

Editor / Tests→Gameplay / UI / Data→Core

위 화살표는 가능한 의존 방향의 예시이며, 모든 모듈이 반드시 모두를 참조한다는 뜻은 아닙니다.
